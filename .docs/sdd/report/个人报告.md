## 2. Baseline 评测与问题定位

实训初期，在阅读 RoCoBench 论文后，我首先完成了环境、模型和评测链路的跑通。由于项目包含 6 个多机器人具身操作任务：

```text
sort, cabinet, rope, sweep, sandwich, pack
```

如果直接开始修改某一个任务，很容易只凭直觉调 prompt，难以判断真正瓶颈。因此我先跑了六任务 baseline，并检查每个 run 中的 `steps*_success_*.json`、prompt、feedback、parser 输出和执行日志。

### 2.1 Baseline 工作内容

我的 baseline 工作主要包括：

- 配置运行环境、MuJoCo/EGL、模型服务和数据输出目录；
- 使用 `run_dialog.py` / `evaluator.py` 跑通不同任务；
- 对 plan / dialog 两种通信模式做对照；
- 记录成功率、失败 step 和失败类型；

### 2.2 失败类型归纳

通过 baseline，我发现失败并不是单一的“prompt 不好”，而是多类问题叠加：

| 失败类型 | 表现 | 影响 |
| --- | --- | --- |
| Parser / 格式错误 | 输出动作名不存在、缺少 PATH、格式不符合 parser | 计划无法进入执行 |
| IK failed | 高层动作看似合理，但机械臂到不了目标位姿 | 任务卡死或反复 replan |
| Collision | 多机器人同时进入共享区域或路径过近 | 执行失败，后续状态变差 |
| Semantic invalid | 动作违反任务规则，如顺序错误、单端放 Rope | 即使能解析也不应执行 |
| Timeout / 空转 | 多轮失败后没有有效进展 | run 到 step 上限仍失败 |

这些观察帮助小组明确：多机器人具身任务不能只依赖 LLM 自由规划，还需要结合任务规则、可达性、IK、碰撞和反馈恢复机制。

### 2.3 Baseline 结果与优化方向选择

仓库中可追溯的部分 baseline 结果如下：

| 模式   | Sort Cubes | Arrange Cabinet | Move Rope | Sweep Floor | Make Sandwich | Pack Grocery |
| ------ | ---------: | --------------: | --------: | ----------: | ------------: | -----------: |
| Plan   |        0/5 |             2/5 |       1/5 |         0/5 |           1/5 |          0/5 |
| Dialog |        1/5 |             1/5 |       0/5 |         2/5 |           0/5 |          0/5 |

其中观察到的部分问题如下：

- cabinet：需要更强阶段规划和物体放置策略
- sweep：工具、垃圾和 SWEEP 阶段容易不匹配
- sandwich：容易出现食材顺序错误或重复动作。dialog 有成功样本，但稳定性不足
- pack： PATH、放置区域、IK 和碰撞问题明显
- rope：绳子自身的柔软特性导致 IK 和碰撞问题明显，路径不合法

## 3. 主要成果：Sort Cubes 任务优化

### 3.1 任务难点

Sort Cubes 要求 Alice、Bob、Chad 三个机器人将不同 cube 放到对应 panel：

```text
blue_square -> panel2
pink_polygon -> panel4
yellow_trapezoid -> panel6
```

三个机器人可达范围不同，跨区域移动必须通过共享 handoff panel 完成：

```text
Alice / Bob 通过 panel3 交接
Bob / Chad 通过 panel5 交接
```

因此，Sort 的难点不是“知道目标 panel”，而是：每一步动作必须符合当前状态、机器人可达范围、交接方向、IK 和碰撞约束。

### 3.2 初始失败现象

在 baseline 和早期实验中，Sort 主要失败包括：

- LLM 输出格式正确但物理不可执行的动作；
- cube 被放到后续机器人无法接手的位置；
- Bob/Chad 等机器人在共享区域并行动作时碰撞；
- 某个机器人 IK failed 后，模型反复输出同一失败动作；
- 执行中出现机器人已经 holding cube，但下一轮仍被推荐 PICK。

这些问题说明，仅靠自然语言 prompt 很难让 LLM 稳定遵守所有物理约束。

### 3.3 解决方案一：Legal Actions 与 Handoff 规则

我首先为 Sort 加入状态驱动的合法动作集合。系统根据当前环境状态判断：

- 每个 cube 当前在哪个 panel；
- 是否已经到达目标；
- 哪个机器人能抓到它；
- 它下一步应该沿哪个方向 handoff；
- 目标 panel 是否适合当前机器人放置。

这样 LLM 不再完全自由生成动作，而是在当前状态下的合法动作中选择。

同时，我加入了方向性 handoff 规则。例如跨区域转运必须通过 `panel3` 或 `panel5`，避免 cube 被放到后续无人可达的位置。这一部分使 Sort 从“自由规划”变成了“受任务规则约束的规划”。

### 3.4 解决方案二：Verifier 与 Failure-specific Ban

在 `plan_prompter` 层，我加入了 LLM 输出前置校验，检查：

- 是否包含 `EXECUTE`；
- 是否每个机器人 exactly one action；
- action 是否属于当前 legal actions；
- 是否多个机器人操作同一个 cube；
- 是否多个机器人放到同一个目标；
- 是否重复之前失败的动作。

早期失败恢复有一个问题：如果 Bob 的动作 IK failed，旧逻辑可能把 Alice 和 Chad 的动作也一起禁掉，导致系统无法执行本来可行的部分动作。因此我改成从环境反馈中识别失败机器人，例如：

```text
IK failed: on Bob
Out of reach: Bob
```

然后只 ban 失败机器人的当前动作，保留其他机器人的可执行动作。这提升了系统的恢复能力。

### 3.5 解决方案三：Partial Fallback、IK 与 Holding Recovery

当 LLM 多次 replan 失败后，我加入 deterministic partial fallback：

1. 优先尝试任务推荐计划；
2. 如果整体计划失败，尝试推荐计划的子集；
3. 如果双机器人组合失败，退化到单机器人动作；
4. 避免一个机器人失败拖垮整轮执行。

此外，我还针对 Sort 的物理执行问题做了补充修复：

- 调整 `panel3` / `panel5` 的共享 handoff 点，使“放的人能放，接的人也能抓”；
- 对 Sort PICK 姿态做放松，减少 cube yaw 或 handoff 后姿态变化导致的 IK failed；
- 增加轻量 IK precheck，提前过滤明显不可行的 PICK；
- 增加 `PLACE <object> <panel>` 形式的 PLACE-only recovery，处理机器人已经 holding cube 的状态；
- 尝试 safe parallel，只允许低风险并行，避免 Bob 与其他机器人在共享区域碰撞。

### 3.6 Sort 实验结果

| 实验版本 | 结果 | 说明 |
| --- | --- | --- |
| `sort_legal_plan_test` | 4/7 成功 | 初步加入 legal action 后仍有碰撞和卡死 |
| `sort_verifier_test` | 10/10 成功 | 串行 verifier 版本稳定性最高 |
| `sort_safe_parallel_test` | 7/10 成功 | 并行提高效率，但稳定性下降 |
| `sort_safe_parallel_recovery_test` | 9/10 成功 | 加入 recovery 和 IK 改进后稳定性提升 |

Sort 的优化说明：对于规则相对离散的多机器人任务，LLM 可以负责高层选择，但必须通过 legal actions、verifier、fallback 和 recovery 机制保证物理可执行性。

## 4. 拓展工作：Move Rope 早期约束与阶段化探索

### 4.1 Rope 任务难点

Rope 任务要求 Alice 和 Bob 分别抓住绳子两端，将绳子越过障碍墙并放入窄槽。相比 Sort，Rope 更难，因为它不仅需要选择动作，还需要输出 PATH，并且 rope 是柔性物体，单端操作会严重破坏后续状态。

### 4.2 早期问题与修复

我在 Rope 早期探索中主要解决了几类基础问题。

第一，模型经常输出不存在的动作名，例如：

```text
LIFT rope_front_end
PLACE rope_front_end groove_left_end
```

但 parser 实际支持的是 `PICK`、`PUT` 和 `WAIT`。因此我修正了 Rope action prompt，明确禁止 `LIFT / PLACE / MOVE` 等非法动作，并将误导性示例改为合法的 `PUT`。

第二，Rope prompt 曾混入 Sort 的 cube / panel 规则，导致任务描述污染。我参与修复了 prompt 生成逻辑，使不同任务优先使用自己的 `central_plan_prompt()`。

第三，Rope 使用 `action_and_path` 模式，所有动作都需要 PATH。原来 prompt 允许 WAIT，但 feedback 又把 WAIT 判非法，前后矛盾。我将 WAIT 统一为合法动作，并要求 WAIT 也带四个路径点。

第四，Rope PICK 目标高度太低时容易撞桌或 IK failed。我将 rope 端点的 PICK 高度改为带上下界的安全高度，减少贴桌面抓取的问题。

### 4.3 阶段化策略：双 PICK -> 双 PUT

Rope 的核心问题是不能单端操作。因此我提出并实现了早期阶段化策略：

```text
阶段 1：Alice 和 Bob 先分别 PICK rope 两端
阶段 2：只有两端都被抓住后，才允许两人同时 PUT
如果只有一个机器人 holding，holding robot WAIT，另一个机器人先 PICK
禁止 PICK 和 PUT 混在同一轮
禁止单机器人 PUT
```

这套策略被写入 prompt、recommended plan 和 feedback 检查中，用于减少 LLM 自由规划导致的 rope 状态破坏。

### 4.4 局限与后续工作

Rope 早期探索虽然减少了非法动作和阶段错误，但仍然存在明显局限：

- IK 对 rope end 抓取位姿非常敏感；
- PATH 点稍有偏差就可能导致碰撞或不可达；
- 柔性物体动力学会放大单步错误；
- dialog baseline 0/5，说明多轮对话不能自动解决底层 IK 和路径可执行性问题。

因此，Rope 的最终优化不能只靠 prompt 或对话协商，还需要更强的路径生成、IK 友好的姿态约束和任务级 deterministic fallback。后续小组成员在此基础上继续优化 Rope，取得了比早期探索更好的最终效果。我的贡献主要是完成早期失败定位、动作空间修复和阶段化分析，为后续优化提供基础。

## 7. 收获与反思

这次实训最大的收获是，我对 LLM 与机器人执行系统之间的关系有了更清晰的认识。

第一，baseline 非常重要。没有 baseline，就很难判断问题来自模型、parser、IK、碰撞还是任务语义。第一天的六任务评测帮助我建立了问题地图，也帮助小组决定优化优先级。

第二，LLM 不能替代任务约束。Sort 的实验说明，哪怕模型能输出格式正确的动作，也可能物理不可执行。因此需要 legal actions、verifier 和 fallback 把 LLM 约束在可执行空间内。

第三，多机器人任务必须重视失败恢复。一个机器人失败时，不应该简单放弃整轮计划，而应该尽量保留其他可执行动作，并通过 partial fallback 推进状态。可以加入反思机制，喂入下一次对话的 prompt 中，减少模型重新犯相同错误的概率。

第四，不同任务需要不同抽象。Sort 更适合离散状态和 handoff 规则；Rope 更依赖阶段协同、PATH 和 IK；Pack/Sweep/Cabinet/Sandwich 又有各自不同的语义约束。因此，通用架构必须允许任务级规则接入。

最后，我也体会到工程协作的重要性。个人分支中的成功经验如果不能与小组架构融合，就很难成为最终系统的一部分。通过第二天的架构讨论和融合，我学会了如何把个人任务级优化转化为小组可复用的方案。
